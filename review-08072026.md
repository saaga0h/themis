# Themis Factory Architecture Review — 2026-07-08

Reviewed material: `CODING_STANDARDS.md`, `UBIQUITOUS_LANGUAGE.md`, `CONCEPTS.md`, the four
skills (issue-writer, split-walker, grill-me, pr-review), plus the pieces the review questions
hinge on — `templates/review.md` (the actual single-pass gate), the test-red skill,
`factory/manifest.txt`, and the runner/tracker code that implements the seams.

Two ground-truth observations from the code up front, because several answers depend on them:

- **The `check` block convention is currently prose-only.** `internal/tracker` parses AC
  checkboxes (`checkboxRE` in `tracker.go:45`) but nothing in the runner or tracker extracts
  fenced `check` blocks or appends them to the verify gate. The issue-writer skill describes
  the mechanism (and references #81), but as of this branch the factory cannot run a declared
  check. Every conclusion below about check blocks is about the *design*, with the caveat that
  the enforcement half doesn't exist yet.
- **The mechanical review tier is narrower than the documents describe.**
  `templates/review.md` is a single-pass gate: a delegated security scan plus an AC-coverage
  grep, emitting only `critical/high/low` ("Do not emit medium"). `UBIQUITOUS_LANGUAGE.md`
  still describes a six-agent Review Battery and max-2 review cycles, and
  `CODING_STANDARDS.md`'s Review Classification section still lists a dozen blocking categories
  the factory gate no longer checks. This drift matters for question 5.

## 1. AC coverage gaps

The taxonomy (behavioural / negative-absence / placement / delegation) handles requirements
whose verification target has a **name or a syntactic signature**. The gaps are the
requirements that quantify over *semantic classes* or express *graded preferences*. Concrete
cases from CODING_STANDARDS.md:

**Semantic-class quantifiers — membership needs judgment, so the sweep AC can't close.**
"Every function that does I/O, blocks, or calls external systems must accept
`context.Context`" (Context section). The exhaustive-enumeration rule works when the class has
a grep signature (`NewDecoder(resp.Body)` does). "Does I/O" does not: a function calling an
injected `Fetcher` does I/O transitively with no syntactic marker. The same failure applies to
"every new error path must have a test that *triggers* it" — enumerating `return err` branches
is mechanical, but "triggers" (versus a test that merely passes near the branch) is not
grep-verifiable. The taxonomy silently assumes grep-able class membership; where it doesn't
hold, the sweep AC degrades into an existence check. Fix that's available without judgment:
for error paths specifically, diff-coverage is real ground truth — `go test -coverprofile`
plus "every changed non-test line is executed by the suite" is a runnable check and
model-independent. That's a fifth AC kind the taxonomy could add (**coverage AC**, backed by a
check block computing diff coverage). For context-threading there is no equivalent; per-issue,
issue-writer can only enumerate the specific functions ("`Filter` and `NewFilter` accept `ctx`
as first parameter" — placement-style, verifiable), and the standing rule stays in the
judgment tier.

**Class-absence — "nothing like X," not "no X."** "Do not clone [a stub] with a different
prefix" (Testing). The negative AC form can kill the *named* failure
(`grep 'issue[0-9]+Stub'` catches the historical naming), but a structural duplicate named
`altFetcherStub` passes every grep. You cannot write an absence check for a thing you can't
name. The rescue is instance conversion at issue-writing time: the issue names the stub to
extend ("new tests use the existing `fakeInvoker`; **no new type satisfying `Invoker` is
declared in `_test.go` files**" — that second clause *is* checkable, by counting interface
implementations in test files). But this demands the issue author knows the current stub
inventory, which pushes a codebase-scan obligation onto split-walker that the skill doesn't
currently state. Worth adding to split-walker's Notes-field guidance: for any slice adding
tests, name the existing test doubles.

**Graded preferences — "prefer," "small," "only when it adds clarity."** "Keep interfaces
small — prefer single-method interfaces where possible"; "Prefer named return values only when
they add clarity"; the interface-vs-function-type rule's "3+" threshold is the *only* graded
rule in the document that committed to a number. These have no AC form as standing rules. They
become ground truth only by **per-issue instantiation**: the human decides at design time
("`IssueQuerier` has exactly two methods: `ListReady`, `State`") and issue-writer freezes the
decision as a placement AC. The rule can't cross the seam; the *decision* can. This is a real
and general finding: the bridge for every graded preference is "decide upstream, encode the
decision," and anything not decidable upstream (message clarity, naming quality) is
irreducibly the human tier's.

**Conditional rules with judgment in the condition.** "Log the failure and continue — do not
abort the loop *unless the failure makes all subsequent items impossible*" (Error handling).
The trailing conditional requires understanding failure semantics. Per-issue, behavioural ACs
pin specific sites ("second issue is processed after the first errors — test asserts both
fetches attempted"); the standing rule is unverifiable mechanically. Same class: the
hardcoded-values carve-out ("defaults are acceptable ONLY when… well-known protocol
defaults") — the grep for literals is mechanical, the exemption is judgment. The practical
bridge there is an **allowlist file**: accepted literals enumerated per repo, anything else
blocks. Judgment moves into maintaining the list (human tier); the factory's check becomes
exact.

**Ambiguous-alias terminology.** The Terminology section is presented as mechanical
("terminology violations… are review failures") but splits in two. Distinctive aliases
(`Executor`, `Processor`, `Stage`, `Guard` as a noun for checkpoint) grep cleanly with
near-zero false positives. Common words do not: `Client` is an alias to avoid for Invoker, yet
`http.Client` is mandatory Go; `Config` is banned unqualified, yet `runner.Config` is
canonical. A word-boundary grep can't tell which sense is in play. So terminology ACs are safe
only for the distinctive subset; the ambiguous subset needs either qualified-form rules (ban
bare `config`, allow `runner.Config` — expressible as a regex, just barely) or stays with the
human.

## 2. The standards-to-AC bridge

Section-by-section assessment. "Mechanical" here means: verifiable by a deterministic command
a shell can run — which is a stronger bar than "an LLM reviewer can check it," and that
distinction is the main point of this section.

| Section | Verdict | Ground-truth vehicle |
|---|---|---|
| Terminology | Split | Dictionary grep for distinctive aliases; ambiguous words are judgment |
| Style (gofmt, naming, error strings) | Mechanical | `gofmt -l`, `go vet`, staticcheck ST1005; "named returns when clear" is judgment |
| Project layout | Mechanical | Path existence checks |
| Dependency injection + direction | **Fully mechanical** | The doc already enumerates the allowed import graph; `go list -deps` diff vs allowlist |
| Interfaces | Split | Consumer-side placement is per-issue placement ACs; "small" is graded (judgment) |
| Error handling | Mostly mechanical | errcheck, `%w` lint, http.Client-timeout AST check; the loop-continue conditional is judgment |
| Context | Mostly mechanical | contextcheck / containedctx lints; transitive-I/O membership is judgment |
| Testing | Split | Filename patterns, per-issue-file ban, `-race`: mechanical. "Correctness-asserting" and stub-sharing: judgment |
| Config/hardcoded values | Mechanical with allowlist | Literal grep + maintained exemption list |
| Security | Split | Secret-scanning mechanical; vulnerability review is judgment (correctly delegated) |
| Commit conventions | Mechanical | Checkpoint already enforces prefixes; order/scope checks are a log parse |
| Prompt templates | Mechanical | Already enforced by `prompt.Substitute` erroring both directions |
| Architecture ("what belongs where", "ignorance is load-bearing") | Mostly mechanical | Same import-graph guard + grep for raw `exec.Command("git"`; "don't move orchestration into prompts" is judgment |

Two structural conclusions follow.

**First: the document's own "blocking review finding" markers track the mechanical subset
almost perfectly.** Every line the standards mark blocking — cross-internal imports, per-issue
test files, missing timeouts, hardcoded infra, swallowed errors — has a deterministic checker
available in stock Go tooling or a ten-line script. That is not a coincidence; it's the
blocking policy working as designed ("contract violations are always blocking" is only safe
policy when violation is objective). But today those checks run as *prose read by an LLM
reviewer* — in the factory (partially, via the old battery, now not at all in the single-pass
gate) and again at pr-review. An LLM re-deriving errcheck from a paragraph is the least
deterministic possible implementation of a deterministic check.

**Second, and the answer to the 18KB question: split the standards into an enforced layer and
a judgment layer.** The pattern for any repo:

- **Enforced layer** — lint configuration, guard tests (the repo already has the shape:
  `factory_assets_test.go` guards the manifest; the dependency-direction section is begging to
  be a `deps_test.go` asserting the import allowlist), and verify-gate commands declared in
  `.themis/workflow.yaml`. These never enter the agent's context; they run in the existing
  green gate. This is not a new review cycle — it's checkpoint machinery, the tier the design
  already trusts.
- **Judgment layer** — the short prose remainder (graded preferences, conditionals,
  "correctness-asserting"), loaded via `{{STANDARDS_DOCS}}` for the human+AI tier and for the
  agent's *authoring* benefit (the agent writing code still benefits from reading "import
  domain types, inject infrastructure operations").

This cuts the per-run context load by well over half, makes the mechanical tier genuinely
deterministic (a lint doesn't vary by model version — directly satisfying the
model-independence constraint), and gives per-repo standards a portable convention: **a
standards rule marked blocking must ship with its enforcement command.** The
manifest/workflow.yaml mechanism already has the slot for this — `Config.StandardsDocs` and
the verify commands are both per-repo declarations; the missing piece is only the convention
binding them.

For the judgment sections, the encoding path is the one from §1: split-walker's Notes field is
where the graded rule gets *decided* for this slice; issue-writer freezes the decision into a
named, checkable AC. The residue that can't be pre-decided — message quality, whether an
abstraction earns its keep — is irreducibly the pr-review tier's, and the documents are right
to leave it there.

## 3. The "less code" problem

The current instruments bound the wrong side of the diff. Negative ACs and check blocks verify
the absence of *named* things; exhaustive enumeration bounds the breadth of *required* change.
Over-engineering is the presence of *unnamed extra* things — you cannot grep for what you
didn't anticipate. Four extensions give ground truth on the surplus side without encoding
aesthetics:

**Footprint ACs (change-surface contracts).** Split-walker already produces a `Scope:`
estimate per slice (`internal/allergen/filter.go` (new), `filter_test.go`, handler
modification). Today that estimate is decorative — it never becomes an AC. Promote it: "the
diff touches only these files/packages," with a check of the form
`git diff --name-only $BASE | grep -vE '<allowlist>'` producing no output. Surplus machinery
almost always means surplus files. The escape hatch is the design's own principle: if the
factory genuinely needs a file outside the footprint, it stops and reports — fail fast and
loudly, discard-and-replan. Use file/package allowlists, not line budgets; line budgets invite
gaming and punish legitimate verbosity, while the file list is a decision split-walker already
made.

**Export budgets (the inverted negative AC).** Instead of enumerating what must not exist,
enumerate what *may*: "package `internal/allergen` exports exactly `Filter` and `NewFilter`;
no other exported identifiers." Checkable by diffing `go doc -short` output or a small AST
walk — this fits the existing check-block machinery verbatim. This is the highest-leverage
single extension, because the canonical LLM over-engineering artifacts — options structs
nobody asked for, an interface with one implementation, a `Manager` type — are all *exported
surface*. The issue-writer already includes interface definitions "where they clarify intent";
elevate those snippets from illustrative to normative. Limitation, stated honestly: it does
not bound unexported machinery — a 300-line unexported helper sails through. Partial coverage,
but the right partial.

**Dependency budgets.** "No new imports in the touched packages; `go.mod` unchanged" —
trivially checkable, and speculative generality frequently arrives with a dependency.

**Test-file immutability at Implement + a diff-coverage floor.** This is the deep one, and
it's an interaction between two existing design commitments. The pipeline is TDD-shaped:
TestRed writes the spec, Implement satisfies it. Two mechanical guards complete the loop the
design already implies: (a) the Implement step's diff must not touch `_test.go` files —
checkable in the checkpoint, closing the hole where the agent widens the spec to fit its
implementation; (b) every changed non-test line must be executed by the suite (diff coverage).
Under those two guards, "the factory implements exactly what the ACs say — nothing more"
acquires ground truth: implementation code not motivated by any test is *by construction* the
over-engineering surplus, and it fails the gate. The agent that adds a speculative error
branch must either write a test for it — surfacing the cost and violating guard (a) — or
delete it. No aesthetic judgment anywhere in the mechanism.

Where it irreducibly fails: over-engineering *inside* the allowed surface — an unnecessarily
general algorithm behind the pinned signature, covered by tests because the agent wrote the
covering test in TestRed. And the deepest form — "no solution is needed at all" — cannot be
caught by any AC structure, because by the time an issue reaches the factory, building is the
contract. That insight lives only upstream, in grill-me, which matches where the leverage
actually is. This half of the problem is irreducibly a judgment problem; the extensions above
shrink the judgment tier's workload, they don't eliminate it.

One caution on the check-block foundation all of this rests on: implement #81's extraction
before layering these on. A convention that binds only through prose is exactly the "telling
is not enforcing" failure CONCEPTS.md §3 warns about, applied to the factory's own tooling.

## 4. Leading words

Candidates, filtered by one admission rule applied strictly: **a leading phrase earns context
tokens only if it has a review-observable signature** — otherwise it's prayer, and
unverifiable prayer is the "guidance over rules" tension at its worst. Ranked by
detectability:

- **"Import domain types, inject infrastructure operations"** (CODING_STANDARDS, DI section).
  Encourages: new capability → interface or function field on `Config`, never a new import.
  Detection: *fully mechanical* — the import-graph guard from §2. The rare leading word with a
  deterministic detector; it should be first in any repo's judgment-layer doc.
- **"A move is done when the old thing is gone"** (issue-writer / split-walker). Encourages:
  destructive half treated as first-class work. Detection: mechanical meta-check (destructive
  AC without a `check` block fails the issue — already specified).
- **"Telling is not enforcing"** (CONCEPTS §3). Encourages: when the implementation carries an
  invariant, the agent adds a guard or test rather than a comment. Detection in review: for
  each invariant stated in a new comment or doc line, does a test or check assert it? A
  reviewer can enumerate new comments containing "must/never/always" and demand the matching
  assertion — semi-mechanical.
- **"Fail closed — absence of a verdict is itself a blocking verdict"** (CONCEPTS §4).
  Encourages: missing/malformed input paths error rather than default-continue. Detection: the
  untested-error-path rule already covers it; review asks specifically "what happens when the
  file/field is absent, and which test proves it."
- **"Progress is measured by commits on disk, not narration"** (CONCEPTS §3). Encourages
  committing over describing. Detection: mechanical — the checkpoint exists precisely for
  this; the phrase makes the agent cooperate rather than fight the gate.
- **"Ignorance is load-bearing"** (CODING_STANDARDS, Architecture). Encourages: don't thread
  cross-layer knowledge; take the field, not the struct. Detection: imports mechanically;
  parameter-width ("received more context than used") is a judgment check the reviewer can
  apply per new function signature.
- **"Broken vs contested"** (CONCEPTS §5). Encourages correct self-classification of findings:
  ground-truth failures blocking, opinion non-blocking. Detection: pr-review's review-notes
  audit measures exactly this — the rate at which factory labels get re-classified by the
  human is a running score for whether the phrase works.
- **"Step transitions are computed, not prompted"** (UBIQUITOUS_LANGUAGE, Pipeline entry).
  Encourages: new control flow lands in Go, not in template prose. Detection: grep templates
  for sequencing/retry language ("if the tests fail, try again") — crude but real.
- **"Stubs are explicit about what they simulate"** (Testing). Encourages purpose-built
  doubles over frameworks. Detection: judgment only (readability of the double). Weakest
  candidate; admit it last or not at all.

Mechanism note: these belong in the per-repo judgment layer (UBIQUITOUS_LANGUAGE already
functions this way — its *definitions* smuggle design stances: "the pipeline is
deterministic," "Ship does not produce a commit"). The portable pattern for other repos: the
terminology table is also the aesthetics table; a definition that states a design commitment
is a leading word with a home. And because the manifest/`StandardsDocs` controls
materialization per repo, each repo tunes its own leading vocabulary without touching the
factory.

## 5. Review determinism

The boundary audit, both directions.

### Judgment hiding in the mechanical tier

1. **Severity assignment is the seam's residual judgment.** The structured-result seam makes
   the *decision rule* deterministic (severity ≥ threshold blocks, absent file blocks), but
   the severity value is LLM-assigned. `templates/review.md` mitigates well by collapsing the
   scale to effectively two classes with definitional membership ("critical/high = a concrete
   vulnerability or an AC with no test; low = everything else; never emit medium") — but
   "concrete security vulnerability" is still a judgment two runs can disagree on. This is
   irreducible for the security half (security review *is* judgment; the design correctly
   fails closed around it). Note also a benign inconsistency: code blocks at `medium` while
   the template forbids emitting `medium` — a prose rule guarding a code threshold. A
   disobedient model that emits medium gets blocked, which is the safe direction, so this is
   fine, but it's worth knowing the guard is prose.
2. **The AC-coverage check is name-matching wearing a determinism costume.** The gate's second
   question — "for each AC, confirm a corresponding test exists — use `grep -n`" — has
   judgment in "corresponding." An AC about a 400 response can match a test that mentions 400
   and asserts nothing; the standards demand *correctness-asserting* tests, but the mechanical
   tier verifies only existence, and which grep the agent chooses varies by run. **The fix
   already exists in the pipeline and is being thrown away**: test-architect produces the
   AC-to-targets mapping with counts, and the test-red skill deliberately keeps it in-context
   ("skeleton files as ceremony"). Persist that mapping as a typed artifact in `.themis/`
   (never committed, exactly like `review-results.json`), and the *runner* can verify per-AC
   test existence mechanically at Review time — same input, same finding, no LLM in the loop.
   This is the single biggest determinism upgrade available, it's the structured-result
   pattern (§4 of CONCEPTS) applied to a seam it hasn't reached yet, and it doesn't conflict
   with the anti-ceremony rule — that rule targeted human-facing skeleton files, not
   machine-consumed seam artifacts.
3. **"Suspect" heuristics.** "A `fix` with no preceding `test` is suspect"; "sparse review
   notes on a non-trivial diff are suspect." Order-checking is mechanical; *suspicion*
   ("non-trivial," "sparse") is judgment. Both currently live in checklist form as if
   mechanical. They're fine where they are (pr-review, the judgment tier) — just don't let
   them migrate into the factory gate, where "suspect" has no defined outcome.

### Mechanical findings hiding in the judgment tier

pr-review §1's contract checks — hardcoded infra, swallowed errors, unthreaded context,
aliased terminology, unbounded reads, missing timeouts, per-issue test files, import
violations — are the §2 lintable set, re-derived by an Opus-tier context on every PR. Moving
them into the per-repo verify gate (not a new review cycle; green-gate commands) does two
things: the factory catches them at Implement time when fixing is cheap, and pr-review's
budget concentrates on what it alone can do — audit classifications, judge over-engineering,
decide the route. The pr-review skill's own framing agrees: its job is auditing *claims*; a
lint's output isn't a claim, so there's nothing left to audit for that class.

### The drift finding

`UBIQUITOUS_LANGUAGE.md` (Review Battery, Fix Cycle, "max 2 review cycles") and
`CODING_STANDARDS.md`'s Review Classification section describe the v1 review loop;
`templates/review.md` and the manifest ("the full review panel is interactive-only now")
implement the v2 single-pass gate. This is a code-as-source-of-truth violation inside the
system whose §7 principle is that prose drifts — and it has teeth beyond tidiness: these
documents are materialized into factory context as `{{STANDARDS_DOCS}}`, so the review agent
in another repo reads a description of a review process that no longer exists. The same drift
risk generalizes to every consuming repo, which strengthens the §2 recommendation: the smaller
the prose layer, the smaller the drift surface.

---

## Summary of hard findings

1. **Implement check-block extraction (#81) before anything else** — every downstream proposal
   (footprint ACs, export budgets, coverage ACs) rides on it, and today it binds only through
   prose.
2. **Persist the AC-to-targets mapping as a seam artifact** and verify AC coverage in the
   runner, not the review agent — the largest available determinism gain, using a pattern the
   design already endorses.
3. **Split per-repo standards into enforced layer (verify-gate commands, guard tests) and
   judgment layer (short prose)** — solves the 18KB load, the model-dependence of
   prose-checking, and most of the mechanical-in-judgment-tier misplacement in one move.
   Convention: a rule marked blocking ships with its enforcement command.
4. **Extend the AC taxonomy with coverage ACs and footprint/export-budget ACs** — ground-truth
   bounds on the surplus side of the diff, where negative ACs structurally can't reach.
5. **Irreducible judgment residue, named**: graded preferences ("small," "clear"),
   semantic-class membership ("does I/O"), correctness-of-assertions beyond name-matching,
   over-engineering inside a pinned surface, and "no solution needed." The first four belong
   to pr-review; the last belongs to grill-me and cannot be pushed downstream at all.

# Addendum — 2026-07-08: backtest results and follow-up questions

Three follow-up questions were raised against the review: (1) backtest the surplus-side
guards against real merged history before building any of them; (2) how do more
Implement-time gates interact with non-convergence, and what is the escape hatch when a
deterministic check is wrong for an issue; (3) size the enforced/judgment split before
committing to it as a sweep.

## A1. Backtest: the four surplus-side guards vs merged themis history

Population: the 31 factory feat commits and 27 issue-merges on `themis-2.0` (issues #6–#85),
plus main's two v1-era merges. Guards A and B were run against commits directly; guards C and
D against the full branch diff of each merged PR compared with the issue body fetched from
Gitea. Coverage runs (guard B) sampled 5 feat commits with full `-coverpkg=./...` suites.

### Guard A — test-file immutability at Implement: **disqualified as written**

7 of 31 merged-good feat commits (23%) touched `_test.go` files, and every one was
legitimate:

| Commit | Issue | Why the test-file change was legitimate |
|---|---|---|
| 966027f | #85 | Move issue — old test file deleted, helper added |
| 7e3d776 | #67 | Dead-code removal — the dead config's tests removed with it |
| 935963c | #64 | Same (dead `AllowedTools` field) |
| d0d1e7e | #44 | Interface change forced stub updates to keep the build compiling |
| f71f2d1 | #52 | Same (signature ripple into `agent_test.go` stubs) |
| 3d97a9b | #62 | Module-path sweep — touches every import path, tests included |
| bd4c7b6 | #39 | The issue's entire scope WAS test helpers |

Root causes: compile-coupling between implementation and shared stubs, and
move/delete/sweep issue classes. A salvageable narrower form — "Implement may not modify or
delete test *functions added by this branch's `test(` commit*" — needs function-level
diffing and still has the stub-signature edge. Not worth building in strict form.

### Guard B — diff-coverage floor: **disqualified as a gate; keep as evidence**

3 of 5 sampled known-good feat commits would have failed a strict "every added statement
line covered" gate. The false-positive classes:

- **Wiring-layer lines** (#85 — `cmd/themis/main.go`): the wiring layer is architecturally
  exempt from unit tests by the repo's own design; any injection change ripples there.
- **Subprocess-adjacent lines** (#83 — inside `GitHubQuerier.ListReadyIssues`): the
  standards *forbid* unit tests from running `gh`; lines there can never be covered.
- **Moves re-attributed as additions** (#65 — 16 "uncovered added" lines in
  `runner_helpers.go` that were relocations out of `runner.go`): extraction issues make old
  uncovered lines look like new machinery. Git rename detection works at file level, not
  function level, so this class has no cheap mechanical fix.

Clean passes: #44 (2/2 covered), #43 (6/6). Verdict: never a blocker. Pilot instead as an
**evidence generator**: compute diff-coverage at Ship, list uncovered added lines in the
PR's Review Notes. "16 uncovered lines, all in moved functions" vs "40 uncovered lines of
new error handling nobody asked for" is exactly the distinction the human tier judges
cheaply — the mechanical tier produces the list, the judgment tier reads it.

### Guard C — footprint ACs: **conditionally viable; pilot at package granularity**

Raw file-level results looked terrible until the false-positive classes were identified,
and all three are instructive:

1. **Doc surfaces**: `ARCHITECTURE.md` appeared out-of-footprint in ~20 of 27 PRs — the
   Docs step touches it. Footprint gates need standing exemptions synced to
   `workflow.yaml`'s doc surfaces. With that one exemption, mature-era issues (#83, #85,
   #68, #67, #64, #61, #46) come out at **zero violations**.
2. **Sweep issues**: #62 (module path, 21 files "out of footprint") and #39 (all test
   helpers) are quantifier-scoped — footprint must support an issue-declared wide/repo
   form, exactly parallel to the exhaustive-enumeration quantifier + sweep-AC pattern.
3. **Wiring ripple**: even mature issues show 1–3 files of legitimate ripple the body
   didn't name — #44 named three `cmd` files but the fix correctly reached
   `internal/tracker`; #65 rewired `main.go`. At file granularity this false-blocks; at
   **package granularity** most of it disappears.

Bonus finding: the footprint check retroactively flags every `runner_issue<N>_test.go` —
it would have caught the per-issue-test-file debt months before the standards banned it.
The gate catches real drift, not just hypothetical surplus. Verdict: pilot, package-level,
allowlist declared per issue by split-walker (its `Scope:` field, promoted from decorative
to normative), standing exemptions from workflow.yaml.

### Guard D — export budget: **viable, but it makes issue names normative**

Where issue-writer's move-enumeration discipline was followed, the gate passes cleanly: #68
added 6 exported identifiers, all enumerated in the body, zero violations. Where the body
under-enumerated, it would have false-blocked good work: #65 (5 unmentioned exports), #61
(3), and early-era issues catastrophically (#11: 21; #37: 7).

The sharpest single finding in the whole backtest: **#65's body proposed `ReadResults`,
`DetermineBlocking`, `BlockingStatus`; the merged code shipped `ReadReviewResults`,
`DetermineBlockingStatus`, `BlockingThreshold`.** Both fine under current rules — the
issue's snippets "clarify intent." An export budget makes those names *contracts*. That is
a real discipline change to issue-writer and to the agent, defensible (names get decided at
design time, by the human) but it must be chosen deliberately, not smuggled in with the
gate. Pilot on move/extract issues first — the enumeration requirement already exists there.

### Aggregate lesson

The two guards that died (immutability, coverage floor) are **repo-standing rules** that
collide with legitimate issue classes: moves, deletions, sweeps, wiring. The two that
survive (footprint, export budget) are **issue-declared parameters**. That is not a
coincidence, and it feeds directly into A2.

## A2. Implement-time gates vs non-convergence

The review treated "move mechanical checks to the verify gate" as pure upside; the #58
failure (two 120-turn Implement runs to zero commits) shows the missing dimension. Every
gate must declare its **retry semantics**, and the backtest gives the placement rule
empirically.

A check belongs at the autonomous Implement gate as a **converge-gate** (bounded retries)
only if both hold:

1. **Self-serviceable** — the agent can always reach compliance by editing code the issue
   already owns; the failure message names file:line and the fix is local. gofmt,
   goimports, go vet, errcheck, curated staticcheck, the http-timeout check, the per-issue
   test-filename ban, the distinctive-alias terminology grep, secret scanning. Retrying
   these is safe because fixing them never requires re-deciding scope.
2. **Issue-independent validity** — the check is right regardless of what the issue is.
   All four backtested guards failed this in naive form; their validity depends on issue
   class (move? sweep? wiring?).

Checks whose *parameters come from the issue* — footprint allowlists, export budgets,
`check` blocks — are a second kind: **abort-gates**. Deterministic, but a failure is
treated as a contract mismatch, not a code defect: **zero retries**, immediate block with a
diagnostic naming the violated parameter ("diff touched `internal/tracker`; footprint
allows `cmd/themis` only"). This answers the non-convergence concern by construction:
abort-gates add zero thrash surface. The #58 failure mode is a converge-loop around
something the agent cannot fix; the rule is that anything not provably self-serviceable
gets no loop at all. (Borderline: the import-graph guard is repo-standing *and* nominally
self-serviceable — "inject instead" — but the fix is a design change; give it one retry,
then abort. `check` blocks are mostly self-serviceable — deleting the old type is local —
one retry, then abort.)

**The escape hatch when a deterministic check is wrong for the issue: there is none at run
time, and there should not be.** An agent that can override a gate turns the gate back
into prose. The escape hatch is structural and upstream:

- **Issue-relative checks**: the parameters live in the issue, so "the check is wrong" is
  definitionally "the issue is wrong" — which routes to the existing discard/amend path
  (Factory Amend, re-split, re-run). Fail-fast is the designed outcome, and with
  abort-semantics it costs one aborted step, not 120 turns.
- **Repo-standing checks**: false positives are handled the way lint FPs are handled
  everywhere — a committed, human-owned suppression list. A run that blocks on a lint FP
  *is* the signal to the human to extend the allowlist; the next run passes. Forbid the
  agent from self-suppressing by making suppression files sit outside every issue's
  footprint by default — guard C protects the suppression mechanism of the other guards.
- **Admission control**: no check enters the Implement gate until it has been backtested
  against merged history (the A1 method, now a repeatable script). The backtest is the
  escape hatch applied in advance.

Never at Implement, regardless of determinism: coverage floors, stub-similarity, anything
with an FP class not yet allowlisted, and every "suspect" heuristic — those stay in the
human tier where "this check is wrong here" can actually be said.

## A3. Sizing the enforced/judgment split

Rule-by-rule classification of `CODING_STANDARDS.md` (344 lines; ~85 distinct rules after
deduplicating the derivative Review Classification and Checklist sections):

- **Fully mechanical** (existing Go tooling or a <20-line script): ≈ 62% of rules
- **Semi-mechanical** (lint exists but needs a curated allowlist / has FP classes —
  wrapcheck, contextcheck, ambiguous-alias terminology, hardcoded-value exemptions): ≈ 17%
- **Irreducible judgment** (graded preferences, "correctness-asserting," loop-continue
  conditionals, stub structural similarity): ≈ 21%

By **prose volume** the mechanical share is ≈ 75%, higher than by rule count, because the
token bulk is precisely the mechanical part: the dependency-direction table (26 lines),
project layout (17), commit conventions (29), the placeholder table (24), the review
checklist (23) are enumerations a gate can own. The always-loaded remainder after a split —
judgment residue plus principle one-liners — is ~4–5 KB against today's 18 KB.

So themis clears the 70% bar by volume and sits just under it by rule count: the split
earns out **for themis**. The honest caveat: themis's standards are enumeration-heavy
because they were written by and for the factory; a greenfield repo's standards will be
thinner and more judgment-weighted, so the ratio does not port. Which is why the sweep vs
rule-by-rule question dissolves: adopt it as a **ratchet convention, paid incrementally** —
any rule marked blocking must name its enforcement command, and no new blocking rule may be
added without one. The fixed infrastructure (one lint config, one `deps_test.go`, the
check-runner) is amortized across all rules and all repos; each repo's mechanical fraction
then reveals itself in migration instead of needing to be estimated up front.

**Dual-purpose rules** (lint-enforceable *and* authoring guidance): the split moves
*enumerations*, not *principles*. Three channels keep the authoring cue alive:

1. The judgment layer keeps the one-line principle with a pointer — "Import domain types,
   inject infrastructure operations — enforced: `deps_test.go`." Fifteen such lines cost
   ~1 KB total.
2. **Gate failure messages quote the principle at the moment of violation** — a guard test
   with a good message teaches exactly when the lesson is relevant, which beats 18 KB of
   always-loaded prose that is relevant to ~2% of any given run. `factory_assets_test.go`
   already demonstrates the pattern in-repo.
3. `UBIQUITOUS_LANGUAGE.md` definitions carry the design stances (review §4) and stay
   loaded regardless.

The residual cost is real and worth naming: moving a cue from prevention (prose read before
writing) to correction (gate fired after writing) spends a fix cycle when the agent
violates. For high-frequency violations keep the principle line loaded; for rare ones let
the gate teach. Violation frequency is measurable from fix-commit history and Loki — so
even that placement decision has ground truth.
